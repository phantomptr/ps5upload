# Pro outage 2026-10-03: triage (CUTOVER §3 gate)

Evidence: the Pro's `/data/ps5upload/stderr.log` (pulled read-only over FTP 2026-10-04) and the
bench logs.

## Timeline
- 08:29-09:01: a run of helper restarts (bench `resume` and manual timing builds). Each new
  instance classified the prior as `wedged`, completed the takeover and **SIGKILLed** the prior
  pid ("reaping crashed prior instance") four times without incident.
- 09:01:44: instance pid 250 starts (a timing-instrumented build); it serves a tiny-file
  download loop (`[ava1] walk / reader` lines) until its log ends.
- 09:10:50: last keep-awake ack (ticks every 15 min).
- 09:14:02: instance pid 251 starts. Takeover: pid 250's FTX2 loops exit ("handed over
  cleanly"), but the reap step **refuses** to kill pid 250 because its ownership record reads
  `started=0` ("previous boot or unverifiable — NOT killing"). pid 251 logs "transfer listener
  ready" and **nothing else ever again**: no AVA1 activity, no breadcrumb, no shutdown line.
- 09:25:50: next keep-awake tick fails; the console answers nothing.
- 11:11:42: console boot (power cycle; the 11:13:42 session reports this boottime).

## Reading
- Not a userland crash of pid 251: a fatal signal writes a breadcrumb; there is none, and no
  clean shutdown either. Silence after a successful start = the console stopped running our
  process, i.e. a console-level hang or panic.
- The only condition unique to 09:14 among that morning's ~20 restarts: **two helper processes
  alive at once with AVA1 running**. Before P3 Task 8 (`ava1_payload_stop`, flag-file takeover)
  a takeover stopped only the FTX2 loops; pid 250's AVA1 server and data layer (mid-download,
  holding :9120 and open files) kept running beside pid 251.
- SIGKILL reaping is not the cause (four clean occurrences that morning).

## Status
- Fixed since: Task 8 (takeover stops the old instance's AVA1 side; node.shutdown runs
  `ava1_payload_stop`), review t8 rounds (no exit mid-Sony-call, replace cooldown).
- Hardening (final review: console): a new instance does not start AVA1 while :9120 is still
  answered by another process; it waits for the takeover, then refuses to run beside it.
- Known limitation (reap by `ki_start`): the kernel start time is in the clock domain of `kern.boottime`, and
  FreeBSD moves both when the clock is set (`settimeofday`, the app's clock sync). After a clock jump a live prior
  helper's `ki_start` can read before the (moved) boottime or in the future; the reap then rejects it as implausible
  and falls back to the ownership record's `started_at_unix`, which is wrong for the same reason or reads 0. The
  prior helper is then NOT killed (a bystander must never be), the new instance finds :9120 still answered, waits
  15 s, refuses to start AVA1 and logs why. Recovery: replace the helper from the app (FTX2 still runs), and if
  that fails restart the console. The `ki_start` offset (336) is also unmeasured on PS5 hardware.
- Open: why pid 250's ownership record read `started=0` (likely the instrumented build).
- Hardware: the restart stress test (CUTOVER §3, 30 restarts per console with jobs running)
  repeats exactly this pattern; run it with the user present.
